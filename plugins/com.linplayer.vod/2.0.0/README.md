# VOD 资源站

把一个影视资源站的**采集接口**接进来，像逛影视 App 一样逛它：分类横条、无限下拉的
海报墙、单击进详情、简介和演职员、多线路切换、点集就播。

**添加服务器 → 插件源 → VOD 资源站**，填接口地址就行，形如：

```
https://某个站/api.php/provide/vod/
```

> 插件不内置任何站点清单，地址得你自己填。

## v2 换了契约

v1 实现的是 `listDir / search / resolvePlay` —— 那是**文件树**的契约，宿主拿它渲染
网盘文件页。资源站硬套文件树，代价是每样东西都得伪装成文件：

| 本来是 | v1 被迫伪装成 |
|---|---|
| 分类 | 文件夹（还占着海报墙的格子） |
| 翻页 | 一个叫「下一页 ›」的文件夹 |
| 「更新至17集」 | 拼进文件名，标题变成「神之水滴 · 更新至17集 · 2026」 |
| 打开 | 文件管理器的**双击** |

v2 改成宿主的**影视目录**契约，四个方法：

```js
ctx.sources.register('site', {
  async categories(server)                     // 分类树   → 顶部横条
  async catalog({categoryId, keyword, page})   // 一页卡片 + hasMore → 无限下拉
  async mediaDetail(id, server)                // 简介/演职员/线路/分集 → 详情页
  async resolvePlay(entry, quality, server)    // 一集 → 可播地址
})
```

**故意不实现 `listDir` / `search`** —— 这个源不是文件树，不该假装是。宿主进源时
探一次 `categories`，通了就走影视浏览页。测试里有一条断言钉着这件事。

## 一个站 = 一个服务器

想用多个资源站，就在「服务器 › 添加」里加多条，每站一条。

这不是偷懒，是插件沙箱的规则：manifest 的出网白名单只写了 `$sourceServer`，
它在运行时展开成**你自己填的那个地址的 origin**。放行谁由你决定，不由插件决定。

## 五个实测出来的坑

**列表接口没有海报。** `ac=list` 每条只回 8 个字段，没有 `vod_pic` 也没有
`vod_play_url`，拿它当列表就得「列 20 条 → 再打 20 次详情」。而 `ac=detail` 同样吃
`t` 和 `pg`，一次给回 20 条 × 83 字段。所以这个插件**从不调 `ac=list`**。
（实测两者耗时几乎一样：0.83s vs 0.75s，瓶颈是 RTT 不是体积。）

**搜索只能用 `ac=detail&wd=`。** `ac=list&wd=` 会**返回全站内容** —— 看起来像搜到了
一大堆，其实一条都没匹配。这个坑很安静。

**有的线路给的是网页播放页，不是流。** 同一部片挂两条线路，一条 `/share/<hash>`
（GET 回来是 `<!doctype html>`）、另一条才是真 `.m3u8`。所以同一部片里只要有一条
线路的地址带媒体扩展名，不带的那些就不摆出来；一条都认不出时（无扩展名直链确实
存在）一条都不丢。

**有的站的分类树是残的。** `class` 里只有 `type_id` 和 `type_name`、**没有
`type_pid`** 的站是存在的。猜不出父子关系时就老老实实全铺在第一级，不编造层级。

**必须自己带 User-Agent。** 宿主的 http 客户端默认一个头都不发，挂了 CF 的站会直接
403，而报错看起来像鉴权失败。

## 出网范围

插件自己只访问你填的那个接口地址。海报由界面直接加载、m3u8 由播放器直接取流，
两者都不经过插件，也就不受白名单约束。
